# Архитектура

В SDK три слоя. Генерируется только средний.

```text
openapi/timeweb-cloud.json     вендорённая спецификация вендора
        │
        │  cargo xtask normalize-spec
        ▼
src/apis/  src/models/          сгенерированный клиент (514 операций, 1006 моделей)
        │
        │  cargo xtask feature-gates
        │  cargo xtask patch-models
        ▼
src/client.rs  retry.rs          рукописный слой
src/pagination.rs  error_body.rs
src/datetime.rs
```

## Сгенерированный слой

`src/apis` и `src/models` получаются из `openapi-generator` генератором
`rust` с библиотекой `reqwest`. Версия генератора зафиксирована в
`openapitools.json`, поэтому повторная генерация даёт тот же код.

Каждая операция — свободная асинхронная функция, которая принимает
`Configuration` и возвращает `Result<T, Error<E>>`. Каждая модель — структура
`serde` с конструкторами, которые генерирует генератор.

## Нормализатор

Спецификация вендора — не совсем то, чего ожидает генератор. Нормализатор —
набор проходов, которые приводят её в порядок перед генерацией:

- **Параметры пути.** Параметр, объявленный `in: path`, у которого в маршруте
  нет `{placeholder}`, из-за чего генератор выдаёт лишний аргумент; а
  `{placeholder}` без объявленного параметра — сослаться на несуществующую
  переменную. Проходы приводят одно к другому и добавляют недостающие
  объявления.
- **Теги.** Все теги написаны по-русски, генератор не может превратить их в
  имена модулей Rust — все операции слиплись бы в один модуль `default_api`.
  Английское имя каждого тега лежит в `x-name-i18n`, и проходы подставляют
  именно его.
- **Объединения.** Генератор превращает объединение из строки и списка в пустую
  структуру, а варианты называет по типу элемента, из-за чего получаются
  идентификаторы вроде `ArrayVecstd::collections::HashMap(...)`. Проходы
  переписывают формы, которые генератор отобразить не может.
- **Ответы.** `response_id` в апстриме — обязательный `uuid`, а API на
  некоторых методах отдаёт `null`; несколько задокументированных тел
  противоречат собственной схеме. Проходы ослабляют эти схемы.

Нормализатор идемпотентен: два прогона дают один и тот же документ.

## Патчер моделей

Генератор идёт по спецификации буквально, а живой API прощает больше, чем
спецификация. Патчер исправляет эту разницу в сгенерированных моделях:

- **Nullable-поля.** Свойство, помеченное как nullable, генератор выдаёт как `Option<T>`
  с `deserialize_with = "Option::deserialize"`, для `serde` всё равно
  *обязательное*: ответ без этого поля падает с «missing field `x`». Патчер
  добавляет `default`, и отсутствующее поле десериализуется в `None`, а
  присутствующий `null` — тоже.
- **Временные метки.** API присылает часть временных меток без смещения UTC,
  которые строгий десериализатор `chrono::DateTime<FixedOffset>` не принимает.
  Поправленные поля используют десериализаторы крейта, которые понимают обе
  формы.
- **Паника.** Сгенерированный `parse_deep_object` обрывает процесс, если ему
  передали не объект. Исправленная версия возвращает пустой список.

## Рукописный слой

Пять небольших модулей несут всё, чего не может генератор:

| Модуль | Что делает |
| --- | --- |
| `client.rs` | Конструкторы: базовые URL, токен, таймаут. |
| `retry.rs` | `TimewebClient`, `RetryPolicy`, джиттер и `Retry-After`. |
| `pagination.rs` | `paginate`, поток по постраничной навигации. |
| `error_body.rs` | `ErrorDetails`, единый формат ошибок API. |
| `datetime.rs` | Десериализаторы, принимающие метку времени со смещением и без. |

## Пайплайн

Вся генерация воспроизводима и живёт в крейте `xtask`:

```sh
cargo xtask normalize-spec openapi/timeweb-cloud.json /tmp/normalized.json
# … openapi-generator …
cargo xtask layout
cargo xtask feature-gates
cargo xtask patch-models
cargo xtask example-tests
cargo xtask api-index
cargo xtask readme
cargo +nightly fmt --all
```

CI проверяет на каждом pull request, что закоммиченный код совпадает с
результатом пайплайна, поэтому ручная правка сгенерированного кода не
проходит незамеченной.

## Еженедельная синхронизация

Еженедельный сценарий сверяет вендорённую спецификацию с апстримом. Когда API
меняется, он перегенерирует клиент, собирает сводку изменений через `oasdiff`,
открывает pull request и мержит его, когда CI зелёный, — если только
`cargo-semver-checks` не найдёт ломающих изменений: тогда pull request
остаётся открытым для ревью.
